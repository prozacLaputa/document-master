# 社区工作坊预约取消（虚构需求讨论稿）

本示例中的产品和规则均为虚构约定，不代表真实系统或已完成开发。

> **允许参加者在活动开始前取消自己的有效预约，取消成功后释放名额。** 本次不增加候补、退款和管理员代取消。跨越活动开始时刻的请求采用哪个判定时点、截止后重复取消的规则优先级、失败后的结果确认方式尚未明确，因此还不能作为完整开发交接稿。

## 1. 范围与约定

角色为已登录参加者；只能查看和取消自己的预约。预约业务状态包括“有效”和“已取消”。活动时间以服务端时间判断；只有当前时间早于开始时间才允许取消，等于开始时间不允许。

入口为“我的预约 → 预约详情”。本次新增取消入口和取消后的结果展示，不改变报名规则。优先级、负责人和上线日期尚未安排。

## 2. 用户确认后，取消才生效

参加者打开自己的有效预约详情；活动未开始时可点击“取消预约”。页面要求二次确认，返回则不改变预约；确认后提交取消请求。成功时预约变为“已取消”，释放一个名额，并展示取消成功及当前状态。

活动已经开始时，取消入口不可操作，并说明“活动已开始，无法取消”。查看他人预约的请求应被拒绝，不显示该预约内容；不能只靠隐藏按钮限制权限。

## 3. 条件与结果

| 条件/动作 | 系统结果 | 数据或状态变化 |
| --- | --- | --- |
| 本人有效预约，取消请求在活动开始前发起并完成处理 | 展示取消成功 | 有效 → 已取消，释放一个名额 |
| 在确认页返回 | 回到详情 | 不变 |
| 有效预约，当前时间等于或晚于活动开始 | 拒绝取消并说明原因 | 不变 |
| 活动开始前，已取消的预约再次提交取消 | 展示当前已取消状态 | 不再释放名额 |
| 尝试读取或取消他人预约 | 拒绝操作，不展示他人详情 | 不变 |

同一预约收到多个取消请求时，要求只释放一次名额；实现方式由技术方案决定。

## 4. 尚未确定的边界

| 未决项 | 对实现与验收的影响 |
| --- | --- |
| 活动开始前发出请求，开始后才处理 | 未确定按收到请求还是处理时刻判定，不能编写唯一预期结果 |
| 活动开始后，对已取消预约重复请求 | 截止拒绝与已取消结果回显的优先级未定；只能确认不能再次释放名额 |
| 请求失败或响应丢失 | 未确定是否允许直接重试、如何查询最终状态，界面不能直接宣称取消成功或失败 |

上述问题须在开发交接前明确；本稿没有替产品选定策略。

## 5. 拟验收场景

| 前提与操作 | 预期可观察结果 |
| --- | --- |
| 本人有效预约，明确在开始前完成取消 | 显示已取消；名额增加一个 |
| 打开取消确认页后返回 | 预约仍有效，名额不变 |
| 有效预约，到达开始时间后尝试取消 | 操作被拒绝，预约和名额不变 |
| 活动开始前，对同一已取消预约重复请求 | 保持已取消，名额不再增加 |
| 同一有效预约的多个取消请求并发到达，且到达与处理均在活动开始前 | 最终为已取消，名额总共只增加一个；具体实现不由PRD指定 |
| 活动开始后，重复请求已取消预约 | 名额不再增加；显示或拒绝规则受上节未决优先级阻塞 |
| 以他人身份访问该预约 | 不能读取详情或取消；名额不变 |
| 请求跨越开始时刻或结果丢失 | 受上节未决规则阻塞，暂不能给确定验收结论 |

以上是验收要求，尚未执行测试；页面原型尚未提供，本文只描述行为。
