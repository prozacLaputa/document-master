# 编辑规范

## 先看文档能否完成读者的任务

确认读者需要理解什么、作出什么决定或执行什么动作。检查开头、标题和章节是否能支持这个任务。
不默认结论前置适合所有文章；叙事、探索型文章可以逐步展开。
大幅重排应说明理由。重要内容即使偏题，也先建议移至附录或另稿，不能自行删掉。

长文先做一份内部工作提纲：各节用途、关键主张、术语、数字及条件。按章节处理后做跨章节复核。提纲用于防遗漏，不默认作为额外交付物。受上下文或读取能力限制时明确检查到的范围，不能把局部审阅称为全文审阅。

## 长文先给结论，再展开支撑

说明、分析、汇报、方案或知识讲解篇幅较长，且必要内容不能再压缩时，默认让读者先抓住主旨再按需深入。不是所有文章都套模板：短文直接说清即可；个人叙事、悬念、探索过程或用户要求原有结构时保留相应阅读顺序。轻量修订不擅自大幅重排，可先提出结构建议。

1. **开头给一个简短结论块。** 用自然、直白且符合文体的话回答“到底是什么／建议怎么做／为什么值得关注”，通常一到三句，不把目录或“本文将从三个方面介绍”当结论。必要条件和不确定性与结论一起出现，不能藏到文末。
2. **正文用分论点支撑。** 每节说明结论为什么成立：分论点 → 证据、案例或推理 → 适用条件和限制。标题尽量让读者看出该节的判断，不全用“背景、分析、总结”等泛标题；不强凑三个分论点。没有依据的部分标待核实，不补造证据。
3. **支持不同阅读深度。** 只读结论块能把握主旨；扫读标题能理解论证路径；细读正文能核对依据与边界。摘要与正文适度重复用于导航是允许的，但正文必须增加支撑信息，不反复换词重述结论。

材料还没有结论时，结论块明确写“目前能确认什么、尚不能判断什么”；不为结论先行而创造共识或替用户做决定。教程的开头可概括核心认识，不强行给行动建议。

### 用视觉强调帮助扫读

- 富文本支持时，开头优先用原生高亮／提示块呈现结论。不要把整篇文章或所有分论点都包进高亮块。
- 加粗用于核心判断、关键数字、重要条件或动作；只强调有区分价值的短语，不整段加粗。
- 红色可标风险、阻塞或未满足条件，绿色可标已验证通过、已完成或满足条件；正文同时写清状态。颜色不能把建议伪装成决定、把预测收益伪装成已实现，也不能用绿字给未经验证的结论背书。
- 颜色适量并保持全文语义一致；遵循目标平台的主题与可读性，不要求固定色值，不只靠红绿区分含义。黑白导出或不支持颜色时，文字状态仍应完整。
- 纯 Markdown 用带“结论”标签的引用块和少量加粗；纯文本用“结论：”与清晰分段。这里的引用块仅作排版容器，不表示外部引用。不输出不受支持的 HTML 或声称已经完成线上高亮。

交付检查：结论块与正文是否一致；每个核心结论是否有支撑；关键限制是否在概览中可见；扫读时能否区分已知、建议与待定。需要示例时参见 [结论先行示范](../examples/conclusion-first.md)。

## 信息保护

每个实质改动回查原文中的：
- 主体与动作：谁做了什么，个人与团队责任是否被混淆。
- 数字与对象：单位、分母、时间窗口、基线、范围和统计口径。
- 状态：计划、进行中、完成、失败、待验证。
- 限定：仅、至少、最多、可能、在某条件下、不包含。
- 关系：因果、相关、依赖、比较方向，结论强度和适用范围。
- 论证：关键背景、备选方案、选择依据、反例、风险与局限。

保留原文引用、代码、公式、接口名和专有名词；怀疑有错时标出，不凭语言习惯改写。
表格、图注、脚注、附件说明也可能承载信息，不能仅检查正文。无法读取嵌入内容时说明遗漏范围。

## 语义与结构

检查指代是否明确、前提是否足够、句间因果是否成立、术语是否同义同名。
同一术语首次出现可解释；缩写仅在确有对应关系时统一。
前后数字不同，先判断时间或口径是否不同，不自行选择一个“正确值”。
重复段落可能承担摘要、强调或操作提示作用；只有不损失独有信息和阅读用途时才合并。重要删除或结论改变先列建议，等待确认。
事实矛盾不靠顺句掩盖：保留有争议的主张，标出冲突位置和需要核对的材料。

## 表达

默认追求高信息密度：同样的信息，让读者更少往返、更快理解。篇幅由必要信息决定，不设统一字数或压缩比例。

交付前逐段问：“删掉这一段，读者会失去哪条事实、理由、条件或必要的理解线索？”答不出来就删除；只是重复前文就合并。先保护信息，再削减措辞：
- 去掉宣布写作意图的开场、泛泛背景、无依据的价值拔高，以及换词复述全文的结尾。
- 把“持续加强协同，全面推动优化落地”换成原文已有的具体动作；没有动作依据就标出空泛处，不编造负责人或计划。
- 汇报和决策材料尽早给出结果、问题或待决策点，随后放支撑依据。教程先交代读者能理解什么；叙事和探索型文章保留展开过程。
- 每段承担一个主要作用。一个观点已讲清就停止，不再加同义解释、比喻、例子和小结凑齐格式；必要背景与因果链不能省略。
- 概览只保留读者需要先知道的内容，正文提供证据与细节。完整清单、重要例外和行动项必须在交付物中可见，不能藏在内部推理里等用户追问。
- 真正有先后顺序的操作才编号；并列事实可用短段落或列表。列表过长按任务分组，不为了“五条以内”删项，也不把所有正文碎片化成项目符号。

错误说明写已观察到的问题、已知原因和可执行检查。原因未查明就写未查明；不为显得干脆而编因果、工期或确定承诺。用户要求详细解释时保留完整推导，压缩无信息文字即可。
不要机械替换禁用词。“核心”“提升”等普通词、合理对比和专业术语本身不是错误。
正式文档保持书面语；个人文章保留原作者节奏和有意重复。去 AI 味不等于一律口语化、短句化或压缩。
不新增所谓金句、宏大框架、价值判断来填空。原文抽象且缺少细节时，可以保留抽象层级并指出缺口。
用户要求只排版、逐字保留时，不进行内容修订；单列内容疑点。

## 事实与证据

分清：原文主张、用户提供的依据、已核对的来源、编辑推断、待核实项。
语言审校不自动保证事实可靠。明确核验了哪些主张，不能笼统声称“全部准确”。
无源数字保留在供审阅稿中并明确标记待核实；不要删除数字后留下更泛的确定断言，也不能补造出处。
外部核验按任务授权及宿主工具规则进行。使用可追溯来源，标明日期或版本；不将内部材料发往未授权服务。
没有核验条件时准确标注，而不是以常识猜测替代证据。
重大疑点影响结论时，停在建议稿；不替用户作最终判断。
