# 技术方案：从评审判断到可执行设计

仅用于技术调研、可行性分析、方案评审与设计交接的叙事组织。继续遵守通用编辑、事实保护、基础排版和质量门槛；不修改配色、图表偏好、间距或确认边界。模板是检查覆盖面的工具，不是必须填满的目录。

## 先确定这份方案要推动哪项判断

优先从用户材料识别阶段和读者，不能因材料缺少排期就阻塞一份选型分析。

| 当前任务 | 主要回答 | 应展开的内容 |
| --- | --- | --- |
| 可行性/选型 | 是否值得做、哪条路径成立、证据缺口是什么 | 约束、真实备选、机制、成本、关键验证 |
| 设计评审 | 设计如何满足要求、边界在哪里 | 整体架构、核心流程、模块职责、异常与兼容 |
| 开发交接 | 如何按已确认设计协作实现和验收 | 接口契约、状态/数据、模块设计、依赖、验收与发布顺序 |

混合文档先满足主读者，再为另一类读者提供后续章节或附录。小改动允许压缩为判断、改动机制、影响与验证三部分，不强加业界调研或完整架构章节。大型重构需明确现状、目标状态和迁移中的中间状态。

## 先建立二级提纲，再展开

按下面的阅读问题组织；可以合并、调整标题，不按调查和开发时间顺序写。大纲应让不了解上下文的评审者看懂问题与方案的联系。同级章节采用相同拆分维度，不混放业务模块、调查动作和文件名。

1. **方案判断**：推荐路径、核心理由、适用范围、关键限制与本次待评审事项。证据不足时写清能确认与不能确认的部分；实现进度不能替代判断。
2. **问题与约束**：用技术视角解释需求和现状差距，不复制整份 PRD。说明目标、不做什么、成功的判定方式及必要术语。预期收益与已验证效果分开；没有量化依据不编收益数字。
3. **选型与取舍**：现状机制为什么不够，真实候选如何满足同一组约束，为什么选此项、放弃另一项。外部调研只保留影响决策的发现与适用条件，不能变成资料摘抄；简单局部改动可省略独立选型章。
4. **整体设计**：先交代参与方、边界、职责和数据方向，再讲一条端到端主流程，随后展开关键分支。每个子流程能追溯到总流程；正常、失败、重试或中断路径按实际材料描述，不因材料不足补造保障机制。
5. **关键详细设计**：按模块或关键技术问题设小节，每节交代职责、输入输出、状态/规则、异常及与上下游的契约。重要接口、数据约束与兼容决策是正文，不等同应移走的文件级改动记录。模块总览可用表格，完整逻辑用可导航的小节，避免整篇设计藏在单元格里。
6. **影响、兼容与验证**：把改动影响连到风险、应对与验收依据。涉及版本迁移时检查旧/新代码、配置、数据的实际组合及回退后可读写性；不能假设“代码回滚”自动恢复数据。只展开相关组合，不机械制造组合矩阵。区分拟验证、已验证和待核实。
7. **落地与待决策**：在材料支持时说明依赖顺序、灰度/放量条件、监测信号、降级和回退条件；阶段安排及负责人仅填已知事实。容量、失败阈值等阻断判断的信息缺失时明确标注，不用一串空白表格冒充计划。
8. **附录与索引**：需求来源、完整接口清单、复现步骤、命令、分支、逐文件变更、详细测试记录与历史版本。正文保留决策所需摘要并就近引用；纯维护元数据通常不占首屏。

## 有条件展开，不照搬业务模板

- 涉及多端、多入口或共享组件：说明同一规则如何保持一致、哪些消费者受影响；不把某个参考团队的具体页面清单变成全局必填项。
- 涉及状态/数据迁移：说明存量与增量的边界、读写兼容、切换和回退限制；未知部分列为待确认，不能以“兼容处理”四字略过。
- 涉及异步交互：按材料检查并发、乱序、重复、超时等适用问题；没有处理策略时如实暴露缺口，不替设计者静默决定。
- 涉及跨服务发布：让发布依赖与灰度、回退顺序对应，不把各方完成日期当作唯一可发布依据。
- 埋点、性能、安全、容量等章节由需求触发；已知不涉及可省略，不能把“没有材料”写成“不涉及”。

删除模板的无用空项、教学提示和示例内容，保留影响判断的真实未知项。不要套用参考文档的组织、人名、业务字段、内部工具、硬性流程或“某种回滚永远禁止”等局部约束。

## 技术方案专用验收

- 只扫二级标题，能否看懂从问题到选择、从整体到细节、从风险到验证的关系？
- 推荐方案是否满足已知约束；放弃备选是否有依据，而非只列优缺点？
- 关键子流程是否接回整体；异常、接口和状态是否前后一致？
- 兼容、切换和回退能否解释关键中间状态，而非只承诺“平滑上线”？
- 当前阶段必要的证据与未知项是否齐全；是否残留空表、教学提示或无关章节？
