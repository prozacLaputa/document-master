# PRD：让需求、行为和验收对应起来

仅用于产品需求梳理、评审与开发交接。继承通用编辑、排版、事实保护和质量门槛；不改变技术方案、分享文章等场景规则。PRD说明产品要发生什么和如何判断符合需求，不代替技术方案决定实现架构。

## 先分清版本阶段

- 讨论/澄清稿：允许未知项，标出对应规则、影响与需要的决策；责任人未知就不填姓名。不能为了让文档显得明确而补规则或删除争议。
- 评审稿：把已确认范围与未决范围分开。需求澄清评审可以讨论未知项，不能宣称未知规则已可直接实现。
- 开发交接稿：阻塞权限、主流程、状态、数据处理和验收的未知项必须解决或将相关范围明确排除；没有授权不替产品决定排除。仍有阻塞项就准确说明未就绪，不把它改写成确定答案。

## 叙事顺序按阅读问题组织

1. **变更概述与边界**：先说为谁解决什么具体问题、本次行为有什么变化、涉及什么范围及不做什么。保留理解取舍所必需的一句背景，长背景和历史材料后置；不以版本表或工作记录占据首屏。不套技术方案的选型结论。
2. **必要概念与角色**：定义新增、容易混淆或改变含义的业务词和角色；少量概念可就近解释，不强制独立术语章。权限说明要区分可见、可操作、可修改及各自对象范围。
3. **业务主链路**：按角色的真实任务串起入口、动作、结果与结束状态，再接关键分支。多步骤关系适合图示；一处文案变更无需强画流程图。图和正文用同一条件与状态名，不逐节点重复读图。
4. **功能范围索引**：功能较多时给总表，标识新增/变更/保持不变、涉及角色和对应详细小节。优先级与负责人只填已提供值，不机械制造P0/P1；少量功能可直接进入详细需求。
5. **逐功能展开**：每个功能设可定位的小节，说明触发入口、前提、主流程、规则、异常和可观察结果；不能把整份PRD塞进一张巨型表格。按下文的功能链路检查遗漏。
6. **数据、状态和页面**：按需列本次新增/变更的业务实体、关键字段、枚举含义与状态变化；页面说明位置、变更、用户操作与系统响应，已有原型就近链接。不要捏造字段名、URL或设计稿。
7. **验收、依赖和未决项**：将要求与可测试结果对应，明确确认状态；非功能指标只写已知目标或标待确定，不能自造性能阈值。元数据、历史、长背景和完整参考索引后置，不填无用空表。

## 逐功能的完整链路

| 问题 | 写清什么 | 常见遗漏 |
| --- | --- | --- |
| 谁、何时进入 | 角色、对象范围、入口、前置状态 | 把能看见误当能操作 |
| 正常发生什么 | 用户动作 → 系统处理 → 可见结果 | 只写按钮和页面，不写业务结果 |
| 条件如何判断 | 条件、优先级、结果，必要时规则表 | 条件重叠却没说明优先级 |
| 不满足或失败如何处理 | 拒绝/保留/重试等已确认行为及状态 | 只写“提示失败”，不说原数据是否改变 |
| 数据怎样变化 | 变更前状态、触发条件、变更后状态和副作用 | 状态图、正文和验收不一致 |
| 怎么判定符合需求 | 前提、动作或事件、可观察结果 | “体验良好”“正常可用”等不可判定语句 |

规则不明时先标问题，不静默选择覆盖、累加、拒绝、取消或自动重试等业务策略。

## 分支与状态的检查方法

围绕材料中实际存在的条件检查正常、边界、互斥和缺省情况；只展开可达且影响结果的组合。对于关键判断，正向与反向结果均应有说明；反向行为缺失时标为待确认，不机械给每句补一个“否则”。

按场景检查权限不足、输入不合法、空/加载/失败、重复动作、并发冲突、超时/截止、撤销和恢复；不把全部项目强塞进每个功能。若时间规则影响状态，写清起算事件、时区/日历口径、截止是否含等号、重试是否重置；材料未说明则标缺口，不能推断。多个地方描述同一规则时用一个定义引用，出现矛盾保留争议并定位。

新增或改变状态时说明“起始状态 → 触发条件 → 目标状态 → 可观察副作用”。区分业务状态、界面状态和后台执行状态；没有既定状态名就用描述，不自造接口枚举。

## PRD与技术方案的边界

PRD保留业务数据的来源/去向、关键字段含义、权限约束、必须满足的行为与验收要求。数据库表结构、详细API参数、缓存、队列和锁实现通常由技术方案说明；已被用户明确指定的技术约束应保留并标明来源，不能以文体分工为由删除。

原型是行为说明的补充，不代替规则。缺少原型可以交清楚的文字交互说明，但不能声称视觉设计已确认；缺少上线时间、负责人不自动阻止讨论稿，也不能补造。

## PRD专用验收

- 概述、功能索引和详细章节是否覆盖同一范围？不做的内容有没有在下文又被悄悄加入？
- 每条关键规则是否连接到触发条件、结果及验收，异常发生后的数据和状态是否明确？
- 不同角色、入口、页面、状态是否矛盾；“保持不变”的范围是否有材料依据？
- 时间口径、优先级或重复操作策略若未定，是否暴露其对实现和测试的影响？
- 条件和验收是否只是草案，还是已确认要求？计划验收不能写成已测通过。
- 文档是否符合当前阶段，而不是靠删除未知项获得“可开发”外观？
